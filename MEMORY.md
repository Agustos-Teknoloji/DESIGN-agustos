## 2026-10-06 header-fold-wide

He saw a mockup of the folded and the full menu. 1280px is the kit's small-laptop breakpoint, so no new breakpoint number enters the kit. A site may not restyle kit classes, so the kit must own the rule. ## 2026-10-03 theme-by-user-choice

The user chooses the theme; the device never chooses it. Emre, 2026-10-03: "user should choose light or dark, not the system to dictate" and "Everything starts with light first". Every page starts light, and a page with no `data-theme` stays light. The optional theme switch (`agustos-theme-switch`, `data-agustos-theme`) lives in `agustos-chrome.js`, which flips `data-theme` and keeps the choice under `agustos:theme`, the key that the adapters and IESDesk already use. A one-line inline head script, published as `kit.json` `themeScript`, applies a stored dark choice before the first paint; a site puts it after the viewport meta and before the stylesheets, with its CSP nonce. The button holds both labels and CSS shows the one it switches to ("Dark theme" or "Light theme"), so a swapped page body needs no repaint; it carries no `aria-pressed`, because a pressed state and a changing name read twice. In the bar it is an icon whose label stays its accessible name; in the drawer the label shows (NN/g: icons need words). The admin pages share the same choice: Emre agreed on 2026-10-03 ("yes") that GEM-agustos-admin moves to the kit switch and the key `agustos:theme` when it adopts v7.7.0, so one choice holds across one address. The checker warns on a page that starts dark (AG024, narrowed from any `data-theme` outside product UI), on `prefers-color-scheme` (AG033), on a switch without the head script before the stylesheets (AG034), and on a switch on a page that does not load `agustos-chrome.js` (AG036). The Astro and Rails adapters lose their own handlers and server-rendered dark (the Astro `theme` prop, the Rails `color_scheme:` option). Why: Emre's rule, and one handler instead of three copies. Rejected: `prefers-color-scheme` as the default, which Emre ruled out; a render-blocking `agustos-theme.js`, which adds a request to every page and a file to vendor; a theme from a cookie, which a static Astro site cannot read; `aria-pressed` with a fixed name, which does not match the spoken "Dark theme" line that IESDesk asked for. Amends 2026-09-29 checker-guards-identity (AG024), and reverses "honors user preference there" (the device setting on product UI) in the archive record v5.0.1 of 2026-09-08 (CTA, dark shipping, photography, quotes). Removes the TODO item "`prefers-color-scheme` for product UI". Reopen only if: a site must follow the device for a legal or accessibility reason, or a site cannot add an inline script. Archive: none.

## 2026-10-01 export-relative-paths

The datasheet, guidelines and social-post HTML reference fonts, lockups and SVG drawings by a path relative to the HTML file (the same `rel_url` in each of the three builders). `rel_url` resolves both ends before it counts the `..` steps, so a symlinked output folder (macOS `/var` is a link to `/private/var`) gets a correct path, and it URL-encodes the result. Raster photos stay base64 data URIs. Why: the absolute `file:///` URLs named the folder that ran the build (a Conductor workspace, then a Claude worktree), so the HTML lost its fonts everywhere else, and every rebuild from a new folder rewrote each path line. The PDF render loads the HTML by file URL, so relative paths resolve there too. Rejected: fonts as base64 data URIs (the three variable fonts add about 1.5 MB to every HTML file, and the PDFs already embed them); a copy of the fonts in each export folder (duplicate files to keep in step); a shared helper module (each builder runs alone, and the tests load it by file path, so a sibling import needs `sys.path` work for a two-line function). Reopen only if: the HTML ships alone, without the `brand/` tree beside it, or a fourth builder needs the function (then move it to a shared module). Archive: none.

## 2026-09-30 astro-passthrough-images

The Astro adapter uses Astro's passthrough image service (`image.service` in `adapters/astro/astro.config.mjs`), so its build does not need sharp. Why: on a Mac with Homebrew `vips` 8.18.7, sharp 0.34.5 finds the system libvips and compiles from source. The compile needs `node-addon-api` and `node-gyp`, so it fails. sharp is an optional dependency of Astro, so `npm ci` removes it, exits 0, and `astro build` fails later on "Rollup failed to resolve import sharp". The lockfile was correct: it lists `node_modules/sharp` 0.34.5. The adapter uses no `<Image>` or `<Picture>`, and every built page stayed byte-identical. Rejected: sharp as a direct dependency (tested: `npm ci` then fails with "Please add node-addon-api", because sharp still compiles against the system libvips); `node-addon-api` and `node-gyp` as dependencies (a native compile on every install, and it needs the Xcode tools); `SHARP_IGNORE_GLOBAL_LIBVIPS=1` in each shell (it works, but each machine must set it, and npm cannot set it from the repository). Reopen only if: an adapter page needs optimized images. Then use the default service and set `SHARP_IGNORE_GLOBAL_LIBVIPS=1` on machines with a system libvips.
